产品经理需要设计能力边界、工具接口、状态、权限与失败兜底。

基本定义

模型能力只是起点。

Agent的最终能力取决于模型、上下文、工具、运行环境和反馈闭环的共同质量。

Model

理解与决策

识别目标、生成计划、选择下一步。

Context

上下文

任务、用户、知识和历史状态。

Tools

外部能力

查询、计算、写入和控制真实系统。

Feedback

结果反馈

观察执行结果并纠错或重规划。

Agent

完成目标

在边界内持续行动直到结束。

Workflow

路径由产品预先定义

适合步骤稳定、规则清晰、错误成本高的任务。优势是可控、可测、易解释。

Agent

路径由模型动态选择

适合步骤无法穷举、需要环境反馈和多工具协作的任务。优势是灵活，代价是更难评测。

产品判断

先判断是否真的需要Agent。

复杂并不等于智能。能用确定性流程解决的问题，不应为了概念而增加自主性。

路径能否穷举
如果步骤固定且异常有限，优先使用Workflow。
是否依赖环境反馈
任务是否必须根据搜索、工具返回或真实状态决定下一步。
是否需要多步规划
用户目标是否需要拆解、排序、重试或跨系统协作。
失败能否恢复
是否可以暂停、回滚、转人工，还是一次错误就产生不可逆损失。
收益是否大于复杂度
自主性是否显著提升任务成功率、覆盖度或效率，足以抵消成本和风险。

合理的演进顺序

单次调用，固定Workflow，带条件分支的Workflow，有限Agent，开放Agent。每增加一级自主性，都要证明业务收益。

系统组成

Harness至少包含六层。

它不是一个单独模块，而是围绕模型建立的运行和约束环境。

Context

上下文构建

组织系统指令、用户状态、业务知识、历史轨迹和本轮目标，控制信息质量与长度。

Tool Interface

工具与接口

定义工具名称、用途、参数、权限、返回结构和错误信息，让模型知道何时用、怎么用。

Orchestration

编排与状态

管理任务拆解、依赖、并行、重试、暂停、恢复、超时和终止条件。

Safety

权限与沙箱

最小权限、身份校验、预算限制、高风险确认、隔离执行和敏感数据保护。

Memory

记忆与反馈

区分本轮状态、长期偏好和可验证事实。只在需要时触发结果检查与重规划。

Observability

可观测与评测

记录计划、工具调用、参数、返回、耗时、成本、错误、人工接管和最终结果。

工具设计

工具接口就是Agent的交互界面。

很多Agent失败并非模型不会推理，而是工具描述含糊、参数不可判定或错误不可恢复。

字段产品问题设计要求
Name模型能否区分相近工具命名具体，避免同义和范围重叠
Description什么时候应该调用写清适用条件、不适用条件和前置状态
Parameters模型是否会填错参数结构化类型、枚举、必填项、示例和校验
Permission这一步能否自动执行只读、可逆、外部影响和高风险动作分级
Response模型能否理解执行结果稳定结构、明确状态码、关键证据和下一步提示
Failure失败后如何继续区分可重试、需补参、需人工和不可恢复
一个好工具的返回
{ status: "needs_confirmation", reason: "external_write", missing: [], retryable: false, next_action: "ask_user" }
安全与失败

先设计失败，再设计成功。

产品方案必须说明Agent什么时候停、什么时候问、什么时候转人工。

理解失败

目标或参数不明确

限制追问数量，要求补齐关键槽位，禁止根据猜测执行高风险动作。

规划失败

步骤错误或循环

设置最大步数、重复调用检测、计划重置和人工接管。

工具失败

接口报错或返回异常

结构化错误、有限重试、替代工具和依赖降级。

权限失败

越权或外部影响

最小权限、动作分级、二次确认、沙箱和审计记录。

验证失败

结果与目标不一致

用代码校验、状态检查或评审模型确认，再决定重做还是结束。

资源失败

成本或时延超限

预算上限、超时、模型降级、缓存和提前终止。

Agent评测

同时评结果、过程与边界。

同一目标可能有多条合理路径，因此不能只比较最终文本。

Outcome

结果是否正确

任务完成率、最终状态、输出质量、用户目标是否满足。

Trajectory

过程是否合理

工具选择、参数、步骤冗余、循环、证据使用和重规划质量。

Safety

边界是否守住

越权率、危险动作阻断率、敏感数据泄漏、确认覆盖率。

Efficiency

成本是否可接受

完成步数、Token、调用费用、P95时延、重试和人工接管。

Grader适合检查局限
Code-based状态、格式、计算、工具执行和确定性规则难处理主观质量
Model-based按Rubric判断正确性、完整性和风险需要校准与一致性验证
Human高风险边界、用户体验和模型分歧成本高、速度慢

60秒回答：怎样设计一个Agent

我会先判断任务是否真的需要Agent。如果路径固定、风险高，我会优先使用Workflow；只有当步骤无法穷举、需要根据环境反馈动态选择工具时，才增加自主性。确定要做Agent后，我会拆成目标理解、上下文、工具、编排、权限、记忆和可观测七部分，尤其把高风险动作、失败兜底和终止条件前置设计。评测上不仅看最终任务是否完成，还会看工具选择、参数、轨迹、安全和成本，并组合代码、模型与人工三类Grader。最后通过灰度观察真实成功率、人工接管和异常分布，证明复杂度带来了业务收益。
